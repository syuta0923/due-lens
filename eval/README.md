# eval（仕様書 4.7）

抽出精度の評価セット。「なんとなく良くなった気がする」で判断しないための正解つきテスト。

用途は 3 つ：**モデルの選定**、**画像の縮小サイズの決定**、**リグレッション検知**。

## 使い方

```bash
# LLM を呼ばずに、ケースの読み込みと縮小後のサイズだけ確認する（API キー不要）
npm run eval -w eval -- --dry-run

# 1 モデル 1 サイズで回す
npm run eval -w eval -- --model gemini-2.5-flash-lite --long-edge 1568

# モデル × 長辺を総当たりして比較表を出す（4.7 の用途 1・2）
npm run eval -w eval -- --model gemini-2.5-flash-lite,gemini-3.6-flash --long-edge 1024,1568,2048
```

API キーは `worker/.dev.vars` の `GOOGLE_GENERATIVE_AI_API_KEY` を読む（環境変数でも可）。
結果は `eval/out/<日時>.json` に残るので、プロンプトを変えた前後で比較できる。

### 主なオプション

| オプション | 既定値 | 説明 |
| --- | --- | --- |
| `--model` | `gemini-2.5-flash-lite` | カンマ区切りで複数指定できる |
| `--long-edge` | `1568` | 送信前に縮小する長辺。カンマ区切り可 |
| `--cases` | 全件 | `--cases 001,003` で絞る |
| `--dry-run` | — | LLM を呼ばない。正解ファイルの検算とサイズ確認だけ |
| `--concurrency` | `2` | 同時実行数。レート制限に当たると結果が歪むので上げすぎない |
| `--today` | 実行日 | 年が書かれていない日付を補う前提（4.1） |
| `--semester-start` / `--semester-end` | `2026-09-28` / `2027-01-29` | 同上 |
| `--thinking` | 指定しない | 思考トークンの上限。`0` で抑制（7.3） |
| `--in-price` / `--out-price` | 内蔵表 | 100 万トークンあたりの USD。円/頁 の計算に使う |

## ケースの置き方

```
cases/
  001.jpg              … 1 ページのケース
  001.expected.json    … 手で書いた正解（Extraction 型）
  002.p1.jpg           … 複数ページは連番。ファイル名順に 1 リクエストで送る（最大 5 頁）
  002.p2.jpg
  002.expected.json
  002.meta.json        … 任意。学期と「今日」をこのケースだけ上書きする
```

ケース ID は最初のドットより前。正解ファイルの書式は
[`cases/000.example.json`](./cases/000.example.json) を写して作る。

**`cases/` の中身はコミットしない**（`.gitignore` 済み）。自分の大学のシラバスそのもので、
著作権と担当教員名などの個人情報を含むため。リポジトリは公開する。

### 集める枚数と中身

5〜10 件。意図的に難しいものを入れる：

- 年が書かれていない日付（曜日クロスチェックが誤りを拾えるかの確認も兼ねる）
- 複数科目が 1 枚に載った課題一覧
- 「第8回」しか書かれていない試験
- 手書きの書き込みがあるもの

## 出力の読み方

```
モデル                      長辺   科目名    date    回数    type   取り零  余計  中央ms   KB/頁   円/頁
gemini-2.5-flash-lite      1568   100.0%   92.3%  100.0%  96.2%      1     0    3821      39    0.21
```

- **科目名 / date / 回数 / type** … フィールド単位の一致率（4.7）。母数は「正解と対応づいた予定」
- **取り零 / 余計** … 予定の取りこぼし・でっち上げの件数。一致率と別に見る
- **円/頁** … 仕様書 7.3 の暫定価格。**モデル決定時は公式の料金ページで確認し直す**

ケースごとの内訳では、外れた値が `date: "2026-11-10" → "2026-11-17"` の形で出る。

## 仕組み

- 精度を上げ下げしない部分（プロンプト・スキーマ・意味の検証・修復リトライ）は
  `worker/src` を import して**本番と共有**している。eval が別実装だと、
  ここで選んだモデルが本番で同じ精度になる保証がなくなる。
- Worker は経由せず LLM を直接呼ぶ。KV も課金も挟まずに総当たりしたいため。
- 画像の縮小は `app/lib/extract.ts` と同じ条件（長辺・JPEG 品質 80）に合わせてある。
- `temperature: 0`。同じ入力で結果が揺れると、比較もリグレッション検知も成り立たない。

### events の突き合わせ

`courses` は名前で照合できるが、`events` には ID が無く、正解と予測で順序も件数も違う。
そこで「どれとどれが同じ予定か」を先に決めてから採点する。

**対応づけに使う項目と、採点する項目を分けている。** `date` で対応づけてから `date` の
一致を数えれば必ず 100% になってしまうため、対応づけには科目名と `title`（その予定が「何か」）
だけを使い、`date` / `session_number` / `type`（その予定の「値」）は採点にまわす。
同名の予定が複数あるときの並べ替えにだけ、日付を補助的に使う。

この採点ロジック自体は `lib/__tests__/score.test.ts` で固定してある（`npm run test -w eval`）。
